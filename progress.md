### 2026-09-11 — Phase 8.3 DONE: Investor Readiness Summary (FR-7.3) — the numbers, and whether they hold up

- **What it is.** **`GET /api/v1/reports/investor?company_id=[&end_month=YYYY-MM]`** plus the screen at **`/reports/investor`**. Where 8.1 answers "what happened in July" and 8.2 "where is this heading", this answers the question a founder actually loses sleep over: *would these numbers survive a first conversation with an investor*. A **trailing year** against the year before it — the investor's unit of assessment; a quarter would let one strong quarter stand in for a trajectory.
- **Judging is not assembling, so it doesn't live in `reports/`.** The grading is a new pure, DB-free module, **`app/financial_engine/readiness.py`**, sitting beside `anomaly.py` because it is the same kind of thing: a **fixed threshold applied to engine output**, not a judgement and not a model's opinion. Six checks — track record, runway, revenue growth, operating margin, revenue consistency, categorized spend — each `ready` / `attention` / `gap`, or `not_applicable`. `reports/service.py` gathers the inputs and carries the verdicts out; it decides nothing.
- **A null figure never grades as a quiet pass.** Runway is null while profitable *and* while out of cash — opposite facts. The first reads `ready` ("the period generated cash, so runway is not the binding constraint"), the second `gap`, and neither is silently absent. Growth with no prior year is `not_applicable`, not +100% against zero.
- **No score, only a weakest link.** `overall_status` is the worst status present. A weighted total would imply a precision this data can't support and invite reading the summary as a valuation — and a healthy margin genuinely does not offset a four-month runway. The page says so on its face.
- **Two derived figures the KPI set didn't hold.** The **annualised run-rate** is the *latest month* × 12, not the year averaged: a run-rate answers "what is this earning now", and averaging in the months before a company started selling understates it (the year's total is printed alongside, so the flattering number is never the only one). The **burn multiple** — cash burned per ₹1 of new revenue — returns null rather than a misleading figure whenever it has no meaning (not burning; revenue flat or down), because 0.00× would read as perfect capital efficiency.
- **Track record is a fact about the company, not the report.** New `service.earliest_transaction_month` (symmetric with `latest_transaction_month`) bounds how long the business has been measurable, and revenue consistency is a share of *those* months — so a nine-month-old company isn't marked inconsistent for the three months before it existed. Uncategorized spend is graded **by value**, not count: one unexplained payroll run matters more than forty unexplained coffees.
- **The thresholds are printed beside the verdicts.** They travel in the response, so the screen states the rule it was actually measured against instead of keeping its own copy — and the page says plainly that they are conventional early-stage benchmarks, not a claim about what any particular investor requires.
- **Shared parts got wider, not copied.** `ReportSections.tsx` took over the period-comparison row and the report formatters (`signed`, `windowLabel`, `runwayLabel`, `MovementRow`) the board page had been keeping privately, and `reports/service.py` grew `_report_company` / `_category_lines` / `_performance_series` once there was a third caller. Two screens stating a period against the one before it must state it the same way.

### 2026-09-10 — Phase 8.2 DONE: Board Report (FR-7.2) — the same figures, for a reader outside the building

- **What it is.** **`GET /api/v1/reports/board?company_id=[&period=quarter|year][&end_month=YYYY-MM]`** plus the screen at **`/reports/board`**. Same assembly rules as 8.1 — engine figures only, no LLM, nothing stored.
- **A trailing window, not a fiscal quarter.** `end_month` defaults to the latest month with data, so "the last quarter" means *of available data*, as it does everywhere else in this system. The alternative — snapping to calendar quarters — produces a two-thirds-empty quarter for any company whose books are kept in arrears, and an empty quarter doesn't read as paperwork, it reads as a collapse. A calendar or fiscal quarter is still one query param away (`period=quarter&end_month=2026-03` is Jan–Mar), so the `fiscal_year_start_month` case is served without the default lying about the business.
- **Both periods are snapshots.** The previous period is the preceding N calendar months and gets its own `kpi_snapshots` row through the same get-or-create, so the comparison is between two objects of the same kind rather than one snapshot and one hand-rolled total. A test pins that both sides are real stored rows and that regenerating mints no duplicates. Calendar-aligning the previous period (matching 8.1's previous-month block) rather than using the engine's day-counted `previous_window` was the one real tradeoff: a window labelled "30 Jan – 30 Apr" because this quarter is three days longer than the last is a window nobody asked for. The engine's `revenue_growth_pct` still uses its own equal-length day window internally — the same window whenever the periods have equal day counts, always for the year — and that's documented in both the module and the architecture doc rather than left to be discovered.
- **Cash is stated at both ends** — `opening_cash` is `cash_on_hand` the day before the period — so `closing − opening` *is* the period's net cash flow by construction. A board's first question is "how much is left and how fast is it going"; stating both lets a reader reconcile the runway's numerator against the period's result instead of taking both on faith. Pinned by a test asserting the identity.
- **Flagged spend is grouped as the rule sees it** — one category in one month — because a board reads exposure ("marketing ran ₹25L above trend in February"), not four card charges. Read as stored, never re-detected, for the same reason 8.1 reads them.

Nothing is re-run: a board paper says what a plan looked like when it was modelled, and re-deriving it against today's data would silently restate the plan on every open. A row whose stored result predates the current shape is skipped rather than guessed at.

### 2026-09-09 — Phase 8.1 DONE: Monthly Financial Report (FR-7.1) — reporting opens

- **What it is.** `app/reports/` stops being a placeholder: `schemas.py`, `service.py`, `router.py`, and one endpoint — **`GET /api/v1/reports/monthly?company_id=[&month=YYYY-MM]`** — returning one calendar month as a structured document: the month's `kpi_snapshots` row, transaction counts, closing cash, a per-category breakdown, the movement against the previous month, a six-month trend, and the month's flagged expenses. The screen is **`/reports`**, linked from the dashboard, `/chat` and `/scenarios`.
- **A report assembles; it never calculates.** The KPI block is not a second computation that agrees with the dashboard — it is the *same row*, fetched through the shared `snapshot_for_period` get-or-create, so generating a report never mints a second snapshot for a month (pinned by a test that generates twice and counts rows). The only arithmetic anywhere in the module is subtracting one already-computed total from another for the month-over-month change. **No LLM touches a report** — architecture §5.4's "(optionally) AI-generated commentary" stays unexercised, and the page says so at the bottom. This matters more here than anywhere else: a report is the artefact that leaves the building, so a figure in one disagreeing with the dashboard is a defect nobody catches until a board meeting.
- **A whole calendar month, always.** Not a rolling 30 days, and deliberately **not** the `companies.fiscal_year_start_month` offset — "the July report" has to mean 1–31 July to everyone who reads it. Because the snapshot is generated for exactly that window, the month's `revenue_growth_pct` is growth against the preceding month and its `burn_rate` is that single month's net outflow, both for free.
- **Nothing is stored, and that's the decision, not an omission.** `schema.md` §10 defines a `reports` table keyed on `file_path` — a record of an exported *file*. Until 8.4 produces one there is nothing to point at, and a row with a null `file_path` would record only that someone once looked at a screen. Every other column is derivable from the request. The real argument is staleness: a report is a pure function of the transactions, so regenerating costs one round of aggregation and can never disagree with the data it describes, where a stored copy can. Documented in `schema.md` §10 so the empty table doesn't read as an oversight.
- **Generation is a read.** Anomaly flags are read as stored rather than re-detected — a `GET` that rewrote `is_flagged_anomaly` would let two people opening the same report see different flags. The `/reports` page re-runs detection on load exactly as the dashboard does, so a report opened directly still isn't quoting stale flags; the decision stays with the screens that own it.
- **Two honesty details that took the most thought.** An **empty month reports** — honest zeros, with undefined ratios left null rather than rendered as a 0% that reads like a measurement — while a company with **no transactions at all** is a `404`, because there is no month to choose from. And the previous-month block carries a **`has_data` flag**: when nothing is recorded for the prior month the changes are differences against zero, which is arithmetically true but means "we have no record", not "the business did nothing". The screen says which one it is.
- **Two new engine helpers, both deterministic, both built to be reused by 8.2/8.3.** `calculations.compute_category_breakdown` is pure and DB-free like the rest of that module — per-category totals plus a share of that category's **own type** (an expense as a % of all expenses; a combined income+expense denominator produces shares that sum to nothing meaningful), income first then largest-first, with a `str(group)` tiebreak so two renders of one report can't reorder. The "Change" column is coloured by whether the news is good rather than by sign (rising expenses red, rising revenue green). **No PDF button**: export is 8.4, and a dead button is worse than none.

### 2026-09-06 — Phase 7.4 DONE: LLM provider behind a swappable interface (FR-6.4) — **Phase 7 complete**

- **What it is.** New **`app/ai_cfo/providers/`**: `base.py` holds the contract — an `LLMProvider` taking the `PromptMessage` list 7.3 already assembles and returning a `Completion`, plus an error hierarchy — `gemini.py` implements it, `null.py` is the disconnected case, and `__init__.get_provider()` maps `LLM_PROVIDER` onto one. It is the **only** module in the codebase that knows a vendor's name; `service.answer_question` asks the registry for a provider and hands it the messages, so a swap is a new file plus a registry line rather than an edit to the feature.
- **Provider: Google Gemini**, `gemini-3.8-flash`, over plain REST with `httpx` rather than the vendor SDK. The interface needs one thing — messages in, text out — and `generateContent` gives exactly that in ~80 lines where every field of the request is visible and testable; an SDK would bring its own auth, transport, retry and telemetry stack, and its own Python-version support matrix, which is a live concern on 3.14. `httpx` was already a dependency for the test client and is now a runtime one.
- **The contract is deliberately narrow.** No streaming, no tool calls, no structured output. That keeps it portable across any chat API, and it leaves the model nowhere to start doing work architecture §4.1 reserves for the Financial Engine.
- **The system prompt travels as Gemini's `system_instruction`**, not as a turn, and the assistant's role is renamed `model`. The FIGURES block is standing instruction rather than something said earlier in the conversation, and a model reading it as a turn can treat it as superseded by later ones. Both mappings are pinned by tests asserting the request body directly.
- **Thinking is off by default.** Gemini 2.5+ reasoning tokens are charged against the same output budget as the answer, so on a small `maxOutputTokens` they can consume the whole allowance and return a truncated candidate containing **no text at all**. This assistant is forbidden from reasoning over numbers anyway, so the budget goes to prose.
- **Failures raise; they are never stored as replies.** Both turns are written in one transaction, so an outage, a rejected key or a blocked prompt leaves *nothing* behind and the endpoint answers **503** — verified by a test that asserts the table is empty afterwards. Writing "sorry, something went wrong" into `chat_messages` would put words in the assistant's mouth in the table that is the §4.1 audit trail, and `replayable_history` would then feed that apology into later prompts. The frontend puts the question back in the composer instead of making someone retype it.
- **Error text is split in two.** `str(exc)` carries the provider's detail — which routinely quotes the API key back at you — and goes to the log; `user_message` is the sentence returned to the caller. A test plants a fake key in the provider's error body and asserts it reaches the log half and not the user half. Retries are decided by the error itself (`LLMError.retryable`): one retry for a 429/5xx/timeout, none for a rejected key or a blocked prompt. That paid off immediately — the very first live call hit a real Gemini 503 ("high demand") and the retry carried it.
- **No key is a supported state; a wrong provider name is not.** An empty `LLM_API_KEY` surfaces as `LLMNotConfigured`, caught in the service, and the inert 7.1 placeholder is stored — a fresh clone and CI both run this way and get a working screen. An **unknown** `LLM_PROVIDER` raises instead: the two look identical on screen and want opposite fixes, and a typo that silently reads as "not connected yet" would sit undiagnosed indefinitely.
- **The banner is asked for, not asserted.** New **`GET /api/v1/chat/provider`** reports `{provider, model, configured}` (no key, ever), and `/chat` reads it. The hard-coded "Not connected yet" notice from 7.1–7.3 was true when written and would have become a lie the moment a key was added; it now names the model, or says no model is configured, because the server said so.
- **A real UX gap surfaced only once answers got slow.** The "Thinking…" indicator lived inside the message-list branch, so on the **first** question of a new conversation — empty transcript — a 15-second model call showed unchanged suggestion chips and nothing else. Invisible while the placeholder returned instantly. Fixed by falling through to the list branch while `sending`.
- **The test suite never reaches the network.** New `tests/conftest.py` forces `LLM_PROVIDER=none` before anything imports settings, so the real key now in `.env` can't turn the suite into billed API calls or break the placeholder assertions written in 7.1. Tests that need a connected assistant inject one through `app.dependency_overrides[current_provider]` — the router exposes the provider as a dependency for exactly that reason.
- **Model choice, honestly.** `gemini-2.5-flash` (the obvious default) **404s for this key** with an upgrade hint — Google retires ids for new keys. The id is therefore **pinned** to `gemini-3.8-flash` rather than tracking the `gemini-flash-latest` alias: this has to work on presentation day, and a retired id is a loud readable failure where a moving alias silently meets a fixed system prompt with different behaviour.

### 2026-08-31 — Phase 7.3 DONE: the AI CFO's system prompt (FR-6.3 / FR-6.5)

- **What it is.** New **`app/ai_cfo/prompt.py`** — pure and DB-free like `context.py` — holding `SYSTEM_PROMPT` and `build_messages(context, history, question)`, which returns the `PromptMessage` list a provider takes. Deliberately three plain roles and a plain dataclass rather than any vendor's type: 7.4 picks the provider, and mapping these into any chat API is trivial, while prompt logic written against one SDK is exactly how a "swappable interface" stops being swappable. The system message is **the instructions, then 7.2's figure block** — that order because the rules govern the numbers, and because a stable prefix is the half a provider can cache.

"So that's roughly ₹50L a year" is a calculation, and a wrong one is indistinguishable from a right one at a glance. - **The disclaimer is deliberately not appended to every answer (FR-6.5).** Boilerplate at the bottom of every message is read once and skipped forever, which is the opposite of *clearly indicating* anything. The two answer the same question from opposite ends — what the assistant is given, and what it's told to do with it. A paraphrase of a rule is not the rule, so the panel shows the text rather than a summary.
- **History handling.** `service.replayable_history` drops the 7.1 placeholder turns before they reach the prompt: every conversation started before 7.4 holds assistant turns saying the assistant isn't connected, and replaying those shows the model a transcript in which it had already refused to help. **Only** the placeholder is dropped, and only because it is inert — real answers are always replayed, including ones quoting figures since superseded, with the prompt stating that only the current block is authoritative. Silently editing what a user was told would be the dishonest fix. That costs a few string joins and buys the guarantee that 7.4 inherits an assembly path already exercised against real conversations and real figures, rather than one that has only ever seen tests.
