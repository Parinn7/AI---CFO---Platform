### 2026-08-31 — Phase 7.3 DONE: the AI CFO's system prompt (FR-6.3 / FR-6.5)

- **What it is.** New **`app/ai_cfo/prompt.py`** — pure and DB-free like `context.py` — holding `SYSTEM_PROMPT` and `build_messages(context, history, question)`, which returns the `PromptMessage` list a provider takes. Deliberately three plain roles and a plain dataclass rather than any vendor's type: 7.4 picks the provider, and mapping these into any chat API is trivial, while prompt logic written against one SDK is exactly how a "swappable interface" stops being swappable. The system message is **the instructions, then 7.2's figure block** — that order because the rules govern the numbers, and because a stable prefix is the half a provider can cache.
- **Why the prompt is mostly prohibition.** The failure this platform exists to prevent isn't a model that sounds unhelpful; it's one that sounds confident while quietly doing arithmetic on the figures it was handed. "So that's roughly ₹50L a year" is a calculation, and a wrong one is indistinguishable from a right one at a glance. So the rule is stated absolutely, with the escape hatch explicitly closed ("even when the arithmetic is trivial, the answer is still no"), and a figure absent from the block "does not exist for you".
- **The disclaimer is deliberately not appended to every answer (FR-6.5).** Boilerplate at the bottom of every message is read once and skipped forever, which is the opposite of *clearly indicating* anything. Two things carry it instead: the standing notice on `/chat`, which no model output can forget or remove, and an instruction to say it **in** the answer that gives advice, in the model's own words, where a person is actually reading.
- **Visible, not just claimed.** New **`GET /api/v1/chat/prompt?company_id=`** returns the standing instructions plus the literal system message, and `/chat` shows the prompt **verbatim** in a second panel, *"The instructions it follows"*, beside 7.2's figures panel. The two answer the same question from opposite ends — what the assistant is given, and what it's told to do with it. A paraphrase of a rule is not the rule, so the panel shows the text rather than a summary.
- **History handling.** `service.replayable_history` drops the 7.1 placeholder turns before they reach the prompt: every conversation started before 7.4 holds assistant turns saying the assistant isn't connected, and replaying those shows the model a transcript in which it had already refused to help. **Only** the placeholder is dropped, and only because it is inert — real answers are always replayed, including ones quoting figures since superseded, with the prompt stating that only the current block is authoritative. Silently editing what a user was told would be the dishonest fix. History is capped at **12 messages** so a long conversation can't push the figures out of the model's attention, and the window is trimmed to open on a user turn (a leading assistant message reads as the model having spoken first; some providers reject it outright).
- **`answer_question` now takes the session, not just the company id**, and assembles the full prompt on every real question before returning the placeholder. That costs a few string joins and buys the guarantee that 7.4 inherits an assembly path already exercised against real conversations and real figures, rather than one that has only ever seen tests.

- **Saving re-runs the simulation server-side.** The client posts only `{company_id, name, period, assumptions}` — never a result — so a stored `result` can only ever be deterministic engine output (architecture §4.1). `simulation_payload()` was extracted so `/simulate` and `save_scenario` emit the *same document*; a test pins `saved["result"] == simulated`, which is what lets one frontend component render a fresh run and a saved one without knowing which it has.
- **The decision that shaped the task: a saved scenario is replayed, not recomputed.** `result` is read back verbatim, so a scenario keeps stating the answer it gave at save time even after the company records new transactions — recomputing on read would silently restate a comparison the user already read and acted on. Reopening one puts its levers back in the form, so "ask this again of today's numbers" is one visible click rather than a side effect. Pinned by a test that saves, uploads more data, and asserts the revisit is byte-identical *and* that a fresh run genuinely differs (so the test isn't passing by accident).
- **Stale-baseline handling.** `baseline_kpi_snapshot_id` reuses the newest snapshot for the same company+period **only if that snapshot still agrees with the freshly computed baseline** (compared at 2 dp, with null≠number); otherwise a fresh snapshot is generated.
